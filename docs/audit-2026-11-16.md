## 一句话结论

功能骨架已经很扎实（真实日期、合并去重、简称、四档等级、三种视图、ICS 导出、69 个测试全绿），**短板集中在三处：日期的「可信度生命周期」没人管、可访问性（对比度/焦点）没过线、几处功能名不副实（站内提醒、locale）**。下面按「必修 → 该补 → 打磨 → 工程」排序。

## P0 · 必修（影响信任与数据安全）

### 1. `verifiedAt` 陈旧无人提醒 —— 这是本插件最该修的一条

赛事日期一年一换，用户之所以愿意信这份日历，全靠「核验日期」这个承诺。现状（直接读 `C:\Users\21232\.dsh\campus-events-calendar\state.json` 统计）：
- **27 条真实事项的 `verifiedAt` 全部是同一天 `2026-11-16`** —— 也就是说这个字段现在等于「批量迁移那天」，不是逐项核验；
- 其中 2 条连 `sourceUrl` 都没有；62 个节点里 `predicted` 35 个、`official_confirmed` 20 个、`unknown` 5 个、`pending_confirmation` 2 个 —— **超过一半是预测**；
- 界面只在详情页 `cc-detail-grid` 里印一行「最近核验：2026-11-16」（`src/client.js:703`）；
- 全仓没有「距今多久」「是否该重核」的判断（搜 `过期|陈旧|stale` 只命中两处字号注释）。

后果：三个月后打开插件，看到的仍是一份「看起来很官方」的旧日历，而 `official_confirmed` 与 `predicted` 在视觉上几乎没有差别。

建议：
- `model.js` 加 `verifiedAgeDays(item, today)`；
- 详情页把「最近核验」做成带状态的徽标：≤90 天「已核验」、90–180 天「该复核了」、>180 天「可能已过期」（用现有 `--cc-l3/--cc-l4` 色系，不新增颜色）；
- 月历上给过期事项的胶囊加一条 2px 虚线左边（与「预测」的虚线边框区分开）；
- 列表/时间轴排序时，把「已过期」的沉到底部并标注。

### 2. 导入是破坏性操作，却没有备份

- `src/host.js:427`：`POST import` 直接 `store.importState(...)`；
- 而合并重复前会先 `store.backup('merge')`（438 行）。

导入会整份替换 `items` + `profile`（界面还弹 `window.confirm('导入将替换当前事项和档案…')`），一旦选错文件就全没了。修法一行：`import` 前 `await store.backup('import')`，并在返回体里带上备份文件名，让界面提示「已备份为 xxx」。

### 3. 通知永不消失 + 弹层不管焦点

- `src/client.js:659` 的 `.cc-notice` 没有任何自动清空：全文件只有 1 处 `setTimeout`，还是 `saveBlob` 里回收 objectURL 用的（第 117 行）。12 处 `setNotice` 都会留下一条要手点 × 的横条。等级、合并、导入这些「点完就该走」的动作尤其别扭。→ 成功类 4 秒自动淡出，错误类保留手动关闭；顺带 `.cc-notice` 已用 `role="status"`，但全文件 0 处 `aria-live`，动态提示对读屏器只有首次挂载会播报。
- `.cc-overlay` 打开后：无 `autoFocus`、无 `focus()`、无 focus trap、无「关闭后焦点还给触发元素」。键盘用户 Tab 会跑到弹层背后的月历里。→ 打开时聚焦弹层标题、Tab 循环限制在弹层内、Escape 关闭后 `focus()` 回原按钮。

## P1 · 该补（功能名不副实 / 规则漂移）

### 4. 「站内提醒」只有开关，没有任何兑现

`state.reminders` 全仓只被读写搬运（`client.js:313/314`、`merge.js:250`、`model.js:176`、`store.js:24/96`、`host.js:510`），**没有一处做到期检查或展示**。点按钮后提示「站内提醒偏好已保存；不会发送系统通知」——等于承认它什么都不做。

两条路选一条，别留着：① 真做：打开插件时算「7 天内到期且有提醒」的事项，在侧栏入口上挂红点 + 顶部一条「本周有 3 件事」；② 改名叫「标记关注」，明确它只是给列表加个星标筛选。

### 5. 表单校验与宿主校验是两套规则，会漂移

`validateItem`/`validateDataset` 只在宿主侧跑（`src/client.js` 里 0 处引用），而 `ItemEditor.submit`（750-760 行）自己手写了一套（标题非空、`official_confirmed` 必须带 `sourceUrl`+`verifiedAt`、`predicted` 必须有 `note`）。两边任何一边改规则，另一边不会报警。

建议：把 `model.js` 的 `validateItem` 提到 client 侧 import（它是纯函数、无 Node 依赖），表单保存前跑一次，把第一条错误显示在字段旁边；宿主侧保留作为最后闸门。

### 6. 三个域文件没接线

- **`src/domain/recurrence.js` 是死代码**：`addAnnualPredictions` 只被 `test/recurrence.test.js` 引用，`host.js`/`client.js`/`store.js` 都不调它。更要紧的是它内部还在造 `accuracy:'month'` 节点（第 53 行）——正是你明确反对的「模棱两可」。**建议直接删**（连同那条测试），或改写成「按去年实际日期 + 官方公告核对后写 exact」。留着它是个定时炸弹：哪天有人接上，数据立刻退化。
- **`locale/zh.json` 没人读**：`package.json` 的 `files` 里列了 `locale`，但 `src/*`、`scripts/*` 零引用。要么接上（所有界面文案走它），要么从 `files` 里删掉——现在属于「装了但没通电」。

### 7. 删除没有撤销

事项删除、备忘删除、重复记录合并，全靠 `window.confirm`。合并前有备份文件，但界面里没有「撤销刚才那步」。低成本方案：删除类操作后，通知条上给一个「撤销」按钮，把刚删的那条原样 POST 回去（数据结构是整条 item，能直接回填）；保留 8 秒。

**另一处旧口径残留（顺手改）：** 数据维护里的「缺口提示」还在教用户猜日期 —— `src/client.js:403` 写的是「只到月份或年份也算数：让 Agent 按往年节奏补一轮，再按主办方公告校对」。这跟你在 m02067 定的规则正好相反（日期必须查、查不到才降级），会把用户引回老路。改成：「这几项只有大致档期。让 Agent 去查一遍主办方公告，查到具体日子再填；查不到就保持现状。」

## P2 · 视觉与交互打磨（有量化依据）

### 8. 对比度不达 AA —— 全站最弱的一环

按当前 token 实测（WCAG 2.1，正文阈值 4.5:1）：

| 组合 | 对比度 | 判定 |
|---|---|---|
| `--cc-faint #93a4ab` / 白底 | **2.58** | 不达标 |
| `--cc-faint` / `--cc-paper #f4f7f8` | **2.40** | 不达标 |
| `--cc-muted #6b7f88` / 白底 | 4.19 | 略低 |
| `--cc-muted` / `--cc-paper` | 3.89 | 不达标 |
| `--cc-teal #168c78` / 白底 | 4.15 | 略低（小字用不了） |
| `--cc-body #3d4f57` / 白底 | 8.56 | 通过 |
| `--cc-ink #1d2b31` / 白底 | 14.56 | 通过 |

而 `--cc-faint` 在 `src/styles.css` 里被引用 **26 次**，几乎全是 10–11px 的正文级文字：星期表头（141 行）、图例（134）、详情页所有 `dt` 标签（361）、`cc-section-count`（366）、节点说明 `small`（371）、等级标签（376/397）、时间轴小字（274）、空状态（253）……（`client.js` 里 0 次，全在 CSS）

修法：把 `--cc-faint` 从 `#93a4ab` 压到 `#7c8f97`（白底 3.37:1、paper 3.13:1，只留给真正的装饰/占位），同时把「标签类」文字全部改用 `--cc-muted` 并把 muted 从 `#6b7f88` 压到 `#5d7078`（白底 **5.18**、paper **4.81**，双双过 AA）；`--cc-teal` 从 `#168c78` 压到 `#12786a`（白底 **5.36**）用于小字链接与选中态。三档文字色的分工保持不动，只调明度——视觉层次不变，每个字都读得清。

### 9. 月历格子里有 42 个「隐形但可 Tab」的按钮

`.cc-day-add`（`src/styles.css:162`）是 `opacity:0` 直到 hover 才现形，但 `opacity` 不影响可聚焦性 —— 预览里实测：**130 个可 Tab 元素中有 94 个在月历网格内，其中 42 个是 `aria-label="在 2026-11-xx 新增…"` 的 + 号**（`.cc-day-add` computed opacity = `0`）。Tab 序列第 24 位进入网格，第 117 位才出去：键盘用户要按 90 多次才能穿过一个月。

修法：默认 `tabindex="-1"`，当所在格获得焦点或鼠标进入时再置 0；或者干脆只保留「选中的那天」显示 + 号（`selectedDate` 已有这个状态）。

顺带：`.cc-day` 本身是 `div`、`tabindex` 为 `none`（实测属性只有 class），`.cc-grid` 也没有 `role` —— 「用键盘选中某一天」只能靠里面的日期数字按钮，读屏器也拿不到「这是第几周」。加 `role="grid"` + 方向键导航是这块的正解。

### 10. 视图状态不记忆

只有 `density` 存了 `localStorage`（`client.js:162/164`）。`view`(日历/已收藏/数据维护)、`mode`(月历/时间轴/列表)、`month`、`filters` 每次重开插件都回到默认。用户如果长期用「时间轴」视图，每次都要点一下。

修法：把 `view`+`mode`+`month` 一起存，加一个 `cc-view` key；`filters` 存但给一个「清除筛选」按钮（已经 `showFilters` 折叠，风险低）。

### 11. 缺一个「年视图」

`mode` 只有 `upcoming`/`month`/`list`。想回答「这一年我有哪些比赛」只能翻 12 次月历或滚一条很长的时间轴。

建议做成「12 个小月历一屏」的年度热力墙：每格只显示日期数字 + 底色（复用现有 `--cc-l1..l4` 的四档色），点某天跳回该月。这是本插件最容易做出「哇」的一屏，而且数据已经全在 `monthIndex` 里，成本不高。

### 12. `src/styles.css` 是「追加式覆盖」，已经开始难改

实测重复定义：`.cc-grid` 4 次、`.cc-calendar-layout`/`.cc-day-add`/`.cc-filters.expanded`/`.cc-shell`/`.cc-sidebar`/`.cc-main` 各 3 次。后 40 多行是逐轮追加的覆盖块，改一个组件要翻三处确认没被压掉。

建议：按「tokens → 布局 → 组件 → 状态修饰 → 媒体查询 → 深色 → 动效」重排一次，同选择器合并；`dist/client.css` 现在 48KB，重排后大概能掉 15–20%。这件事不必一次做完，可以跟着下一个视觉改动顺手做。

- `prefers-reduced-motion` 全局禁用动效已做；深色主题 token 完整。

## 建议的动手顺序

1. **P0 三件**（各 1–2 小时）：导入备份 → 通知自动消失 + 焦点管理 → `verifiedAt` 陈旧提醒。这三件直接决定「这插件能不能被信任地长期用」。
2. **P1 第 6 条**：删 `recurrence.js`（防止数据退化）+ 决定 `locale` 去留。
3. **P2 第 8 条对比度**：只调 4 个 token 的明度，全站立刻变清楚，改动面极小、收益最大。
4. **P2 第 11 条年视图**：这是唯一一个「用户会主动截图分享」的新功能。
5. 剩下的（撤销、视图记忆、CSS 重排、发版）可以合并成一个 0.2.0 版本一次做完。
