# 面向多 Agent 并行软件开发的共享工作台

## 研究与实践设计

- **版本**：1.0
- **日期**：2026-10-28
- **状态**：设计稿，尚未实现或实测
- **目标受众**：使用多个不同用途 Agent 共同开发同一软件项目的独立开发者和 AI 爱好者

## 1. 摘要

本项目拟设计并验证一个跨 Agent 的轻量共享工作台，作为 MCP 服务提供统一的项目状态、任务上下文、决策记录、阻塞项和交接记录。研究核心是：在多个 Agent 并行参与软件开发时，结构化共享状态与交接机制能否降低上下文不同步导致的重复劳动、过期决策和集成返工，同时不引入过高协作开销。

首期不负责自动拆解或分派任务、不执行代码、不锁定文件、不自动仲裁分歧，也不提供网页看板或实时推送。建议以共享项目目录中的 Markdown 记录作为权威数据，由 MCP 工具提供受校验的读取和写入接口。该选择暂时只适用于 Agent 能访问同一目录且不要求实时协作广播的情形。

## 2. 背景与问题陈述

多个 Agent 在同一项目中并行工作时，常见协作失效包括：重复实现同一任务；依据已经变化的要求或技术决策工作；不知道其他 Agent 正在修改哪些文件；交接缺少验证证据；负责人难以判断结果能否集成。单纯增加 Agent 数量不能保证吞吐提升，沟通和冲突成本可能抵消并行收益。

本设计将研究范围限定为“共享状态与结构化交接”这一可独立验证的机制，不在首期同时引入自动调度、工作区隔离、文件锁或云端协作服务，以便将实验结果归因于该机制。

## 3. 目标与非目标

### 目标

1. 提供人和不同 Agent 可读取、更新的共同项目协作状态。
2. 让任务目标、验收条件、负责人、状态、计划文件范围、决策、阻塞、交接及验证证据可追溯。
3. 在写入冲突或信息过期时显式报告，而非静默覆盖。
4. 通过真实开发任务前后对照，量化质量、效率、冲突和协作开销。
5. 以 MCP/TypeScript/Node.js 为首发技术方向，保持存储和 Agent 客户端适配边界清晰。

### 非目标

- 自动判断最佳任务拆分或自动分配 Agent。
- 强制文件锁、自动合并代码、自动解决方案分歧。
- 托管式数据库、多人 Web 看板、跨机器实时广播。
- 替代 Git、Issue 跟踪器、CI 或 Agent 自带的任务机制。
- 在没有测量之前承诺性能提升或任务成功率提升。

## 4. 研究问题与假设

**主研究问题**：相对于 Agent 使用现有工作方式，启用共享工作台是否减少上下文不同步带来的重复工作与返工，并保持最终任务质量不下降？

待检验假设：

- H1：启用工作台后，每项任务的重复实现或重复调查事件数下降。
- H2：启用工作台后，因依据过期决策或漏掉依赖而产生的返工次数下降。
- H3：启用工作台后，交接内容完整率上升，验证阶段发现的可归因于交接遗漏的问题减少。
- H4：协作记录和状态维护增加的时间不会抵消返工节省；以每个验收通过任务的总人机时间衡量净效率。
- H5：最终验收质量不低于基线；若出现质量下降，即使耗时更短也不判定为成功。

这些假设是实验问题而不是已证实结论。

## 5. 适用场景与边界条件

首轮适用：功能开发、测试补充、缺陷修复或代码审查等可以拆分为至少两个相对独立工作单元的任务；Agent 能访问相同项目状态文件；有用户或负责人检查验收结果。可使用不同 Agent 产品，但首轮实验应尽量固定 Agent、模型版本、提示词、工具权限和任务类型。

不适用或需要单独设计：Agent 分布在不可共享的不同工作区；必须实时通知状态变化；对状态有严格事务或强一致性要求；协作记录不得进入项目目录；工作内容高度敏感且本地存储策略未审查。

## 6. 角色与责任

- **负责人/集成者**（用户或主 Agent）：定义目标、范围和验收标准；建立任务；处理任务边界重叠和决策争议；最终决定是否接受、返工或集成。
- **实现 Agent**：开始前读取相关当前状态和决策；声明任务及计划涉及的文件/模块；完成后提供改动摘要、验证命令及结果、遗留问题和交接记录。
- **验证 Agent**：依据验收条件独立验证实现；报告发现及证据、严重程度和复现方式；不直接覆盖实现者的工作。

角色是职责标签，不要求一类 Agent 必须绑定特定供应商或模型。为降低实验混淆，首轮尽可能不变更角色配置。

## 7. 协作流程

1. 负责人建立项目目标、任务、验收条件和依赖；任务边界尽量明确。
2. 实现 Agent 读取当前状态、相关决策及阻塞项，检查文件范围重叠，并登记计划。
3. 若检测到任务范围重叠或关键决策不一致，系统发出提示；Agent 暂停扩展冲突部分并提交说明，由负责人调整顺序、范围或方案。
4. 实现 Agent 执行任务，并在约定节点更新状态；重要方案变化必须记录决策与理由。
5. 实现 Agent 提交结构化交接：完成内容、涉及文件、验证证据、已知限制、未解决问题和建议下一步。
6. 验证 Agent 按验收条件检查，并报告通过/失败及证据。
7. 负责人决定接受、返工、拆分或重新分派，并更新任务最终状态。

系统只做信息组织、校验和冲突提示，不静默替人作决策。

## 8. 信息模型与交互机制

项目状态至少包括：

- 项目目标、当前范围、验收原则及更新时间。
- 任务：稳定 ID、标题、描述、验收条件、状态、负责人、依赖、计划文件/模块范围、创建及更新时间。
- 决策：稳定 ID、问题、选择、理由、状态（有效/被替代）、记录者、时间和关联任务。
- 阻塞项：描述、影响任务、责任人、状态和解决记录。
- 交接：任务 ID、摘要、变更范围、验证命令与结果、风险/遗留项、提交者和时间。
- 事件历史：关键创建、状态变化和决策变更，以便审计和实验计数。

首版建议使用按实体拆分的 Markdown/JSON front matter 记录，避免多 Agent 频繁改写单一大文件。每次写入应包含实体 ID 和预期版本或更新时间；版本不匹配时返回冲突，调用者重新读取并显式处理。字段 schema、ID 规则和写入原子性需在实现计划中确定。

MCP 工具能力按职责划分：读取项目/任务/决策、创建或更新任务、记录决策、登记阻塞、提交交接、获取变更或冲突摘要。工具应校验必填字段、状态迁移和项目根目录边界，并提供清晰错误而不是部分成功。

## 9. 数据存储选择

### 首版推荐：共享目录中的 Markdown 记录 + MCP 读写接口

判断依据：个人/小规模实践、低部署门槛、人工可读、便于备份和检查；适合先验证协作机制是否有价值。可选择纳入 Git 以保留历史，但 Git 提交不等于实时同步，也不自动解决并发写冲突。

| 机制 | 适用条件 | 优点 | 限制/成本 |
|---|---|---|---|
| Markdown 文件 + MCP（首版） | Agent 共用本机项目目录；低并发；不要求推送 | 人可检查、无额外服务、易备份，可选 Git 历史 | 不原生实时通知；同文件并发写须检测；不自动跨机器同步；结构查询较弱 |
| SQLite | 单机频繁结构化并发读写、需事务与查询 | 事务、约束和查询能力更强 | DB 文件不便 Git 合并；仍需明确本地共享方式；实现复杂度更高 |
| 远程数据库/API | 多机器、多工作区或集中访问控制 | 可跨机器访问、统一认证和服务端查询 | 运维、认证、网络依赖、成本与安全面增加 |
| 看板/实时协作服务 | 需要人类可视化管理或状态推送 | 易观察、可通知、适合团队协作 | 首版范围膨胀；需前端和服务端；不能只凭界面解决 Agent 遵循问题 |

若确认跨机器或实时同步为硬需求，应重新评审存储方案，不能继续把 Markdown 本地文件描述为充分方案。

## 10. 性能定义、初步估算与目标

目前没有实现、压测、明确机器规格或部署环境。以下不是实测值，只是基于 Node.js/TypeScript、本地 MCP 服务、小型 Markdown 记录和同机共享目录的**待验证估算**。操作系统、MCP 宿主、依赖体量、磁盘、杀毒软件、Agent 调用频率及记录大小都会影响结果；模型推理不属于工作台性能。

| 场景 | 初步估算/定义 | 不确定性 |
|---|---|---|
| 页面首屏/交互 | 首版没有 Web UI，不适用 | 未来加入 UI 后单独定义首屏和交互指标 |
| MCP 服务冷启动 | 粗估 0.2–1.5 秒 | 宿主启动策略、依赖加载和设备差异大，必须实测 |
| 单次状态读/写 | 服务处理粗估 5–100 ms；含 MCP 往返粗估 20–300 ms | 未实测；需明确调用链、文件大小和 fsync/原子写策略 |
| Agent 间状态可见性 | 写成功后，其他 Agent 下一次读取时可见；无主动推送 | 可见延迟由消费者下一次读取时间决定，不应称实时同步 |
| 任务端到端耗时 | 从任务开始到验收的墙钟时间及人机主动操作时间分别记录 | 受任务难度、模型波动、排队和人工等待影响，不能归因于工作台单一因素 |
| 并发吞吐/一致性 | 记录成功操作/秒、错误率、冲突率和丢失更新数 | 并发模式和负载未定义前不报吞吐承诺 |

**候选验收目标（不是已有性能）**：本地测试、最多 5 个并发 Agent、单条记录不超过 100 KB 时，状态读写端到端 P95 ≤ 500 ms；并发更新不得静默丢失已确认成功的记录。压测报告应给出 P50/P95/P99、成功率、吞吐、冲突数与数据一致性结果，并说明硬件、操作系统、Node 版本、MCP 宿主、数据规模和测试脚本/步骤。

性能验证矩阵：1、3、5 并发 Agent；分别测试只读、各自写不同任务、竞争更新同一任务；每组至少重复 5 轮，预热与冷启动分开报告。样本量不足时只报告探索性结果，不做显著性推断。

## 11. 效果评估方案

### 实验设计

采用真实项目任务前后对照。建议先选 6–10 个可比较的小到中型开发任务；一半使用当前基线流程，一半使用工作台流程。若任务难度可分层，则在难度相近的任务间交替分配条件，减少时间趋势影响。若任务总量不足，应明确标为探索性案例，不宣称普遍因果结论。

固定或记录：Agent 数量与角色、模型/版本、提示词、工具权限、代码库状态、任务类型、验收条件和负责人介入规则。记录每项任务的起止时间、主动操作/沟通时间、工具调用数、状态更新数和返工原因。任务结果由不知道条件的审查者按同一量表评分（若可行）。

### 指标定义

| 维度 | 指标及计算方法 |
|---|---|
| 完成质量（主护栏） | 验收通过率 = 首次或最终满足全部验收条件的任务数 / 完成任务数；另报告缺陷数、测试通过率及盲审质量评分。质量下降则不能以速度提升判为成功。 |
| 效率（共同主指标） | 每个最终验收通过任务的墙钟时间；另报告主动人工时间/沟通时间，分别给中位数和范围。 |
| 返工 | 返工事件数/任务；返工分钟数；按原因（过期决策、遗漏依赖、重复实现、接口不一致、缺陷等）分类。 |
| 重复劳动 | 可判定为重复的代码/调查/测试工作事件数，以及估计重复耗时；事先约定判定标准，抽样双人编码。 |
| 冲突 | 任务范围重叠次数、决策冲突次数、同文件/同接口冲突次数、导致等待或返工的冲突比例及解决时间。 |
| 交接质量 | 交接必填项完整率；验证者因信息不足追问次数；交接遗漏导致的问题数。 |
| 协作开销 | 写入状态、读取状态、处理冲突所耗时间；每个任务的工作台操作次数；记录维护时间占总主动时间比例。 |
| MCP 性能 | 端到端读写延迟分位数、错误率、吞吐与并发数据一致性，依第 10 节方法测量。 |

主要分析采用每个任务配对/分层的中位数差异和原始数据展示；任务少时报告个案与范围，不用单一平均值掩盖离群。所有指标定义和排除规则应在采集前固定。

### 最低成功判据（建议，实验前确认）

1. 工作台组验收质量不低于基线组，且没有新增严重缺陷。
2. 重复劳动或由上下文不同步导致的返工至少下降 20%，或交接完整率提高至少 25 个百分点；至少一个主要协作指标达到门槛。
3. 每个通过任务的主动时间没有因工作台操作增加超过 10%。
4. 性能与一致性达到第 10 节候选本地目标，或明确记录未达标及瓶颈。

这些阈值是建议的决策门槛，不是既有结果；应在正式实验前由项目负责人确认，避免事后挑选有利指标。

## 12. 难点与风险控制

- **Agent 不更新/不读取状态**：工作流要求开始前读取、交付前更新；记录缺项并统计遵循率。低遵循率时先改提示和工具易用性，不应直接认定机制无效。
- **并发写覆盖**：按实体拆分记录；使用版本检查和原子写；冲突返回可恢复错误；压力测试竞争更新。禁止无声 last-write-wins。
- **状态过期**：提供更新时间、决策有效/被替代状态和变更摘要；调用者发现版本变化后重读。
- **实验混杂**：固定模型与流程；任务配对/分层；记录任务难度及人工介入；报告样本量和限制。
- **评估偏差**：预先定义指标和门槛；尽可能盲审；重复劳动等主观分类采用明确编码规则并双人抽查。
- **隐私与知识产权**：默认本地存储；明确记录可能包含项目路径、摘要和代码信息；不记录密钥；提供排除规则和清理方式；纳入 Git 前由用户确认仓库策略。
- **范围蔓延**：首版不加远端同步、自动锁、自动任务拆解或 UI。若关键需求证实依赖这些能力，重新拆分设计，不暗中扩张 MVP。
- **性能误读**：标注估算、目标和实测三种状态；只有可复现的测试报告才能称为实测。

## 13. 实施与验证步骤

1. **需求确认**：确认 Agent 是否共用同一机器/目录、并发数量、实时性要求、数据敏感度和记录 Git 策略。
2. **冻结实验协议**：确定任务选择、基线工作流、Agent 配置、指标定义、成功阈值、采集字段和排除规则。
3. **建立基线**：在不使用工作台的条件下完成首批任务，记录同一套指标。
4. **实现最小工作台**：实现实体 schema、MCP 读写工具、版本冲突检测、结构校验、审计记录和本地存储；不实现 UI/实时推送/自动调度。
5. **功能与安全测试**：验证状态迁移、权限边界、路径边界、错误恢复、并发写无静默丢失、敏感信息处理及备份/清理方式。
6. **性能测试**：按第 10 节矩阵运行，发布硬件和软件环境、数据规模、分位数、吞吐及原始结果摘要。
7. **工作台组试用**：用匹配任务和固定 Agent 流程开展实验，保存必要的去敏日志和结果。
8. **分析并决策**：对照预先确定的门槛，判断保留 Markdown、转 SQLite/远端方案、改进交接机制或停止扩展。
9. **发布研究报告**：披露样本数、任务类型、版本、测量方法、原始汇总数据、偏差和外推限制；不把小样本探索性结果写成普遍结论。

## 14. 必须补充的信息

在进入实现和压测前确认以下信息：

1. Agent 是否运行在同一台机器并访问同一工作目录？若不是，是否可共享网络存储？
2. 通常同时活跃的 Agent 数量、读写频率及是否会同时编辑相同任务？
3. 是否要求主动实时推送，或任务开始/交接时读取即可？
4. 项目记录能否写入工作区及 Git？有哪些敏感数据禁止记录？
5. 可用于前后对照的真实任务数量、任务类型和可接受的负责人投入时间？
6. 最终首发对象是个人本地使用还是团队跨机器使用？

若答案显示必须跨机器或需要实时推送，应先重做同步架构选择，再继续技术实现和性能承诺。

## 15. 当前结论

当前推荐将项目定位为“本地共享目录上的 MCP 协作记录与交接层”，先用 Markdown 实现、显式检测并发版本冲突，以真实项目任务做小规模前后对照。其优势假设是部署门槛低、数据可读、可快速验证；尚未证明其能提升效率，也尚未获得任何真实性能数据。首轮验证的核心不是追求最大 Agent 数量或做完整看板，而是确认结构化状态是否降低了可观察的重复劳动和返工，且工作台本身的记录成本可接受。
